# Final host, bridge and release design review

Date: 2026-10-14. Outcome: approve the shared-engine direction after the three contract corrections below. This is a document review, not implementation approval or host acceptance. References identify lines in the reviewed [integrated design](../design.md).

## Material corrections

1. **Separate owner credentials from model-scoped callers.** Sections 6–7, lines 251, 277 and 293, give the CLI an owner-only capability record while forbidding model identities from grant/registration/registry acceptance. They do not define how a host skill's CLI invocation becomes a restricted caller rather than an owner. Filesystem ownership alone cannot distinguish those two callers running as the same user. A model that can obtain the owner capability could bypass the stated operation restriction. Specify separate owner and delegated credentials, with server-side project/run/operation limits, expiry and revocation. Owner credentials must be inaccessible to model-controlled tools; delegated CLI calls must never fall back to reading the owner record. Owner grant expansion remains an authenticated owner interaction. An ambient host unable to maintain that separation must not receive privileged engine access or be counted as a verified restricted invocation. Add the escalation attempt to A4/A10. **R4.4–R4.5, R4.8, R4.16, R6.3, R6.10.**

2. **Define HTTP attachment during headless ownership.** Sections 1–2 and 7, lines 16, 57 and 277, choose one HTTP transport but allow an in-process headless CLI owner. Competing clients are instructed to attach to its endpoint; the draft never requires that this owner serves one. A headless run could therefore hold the lifetime lock while leaving dashboard/CLI attachment unavailable. State that every online engine owner, including a headless invocation, exposes the same authenticated HTTP API and publishes its endpoint only after readiness. Define orderly owner exit when attached clients or accepted work remain; do not imply that a short-lived CLI can exit while its scheduler continues. Offline snapshot inspection remains a separate read-only mode. Exercise dashboard attachment during a headless audit in A6. **R5.15–R5.16, R6.10–R6.12, R7.13.**

3. **Choose the proposal ingestion contract.** Sections 3 and 6, lines 182–205 and 261–265, require closed typed commands and engine-mediated proposals, but do not specify which native bridge output becomes a proposal. The preserved review names CLI/MCP access and warns about experimental dynamic tools; the master has not selected an action path compatible with its restricted agent. Before implementing the bridge, choose one versioned proposal envelope and its transport: validated structured assistant output or a documented restricted tool channel. Bind it to the engine-owned conversation/context revision, retain actual diff content alongside its digest, and reject malformed/unknown proposals before dispatcher submission. Ordinary deltas and native tool notifications remain discussion/progress only. No native direct apply is permitted; the shared executor retains preimage/version checks. Validate ingestion separately from containment in A1/A4. **R5.17–R5.19, R6.10, R7.12.**

## Approval and remaining gates

The single HTTP architecture, receipt-owned conflict-safe installation, allowlisted release artifacts, controlled one-file executor and separation of skill discovery from dashboard bridges are acceptable. Existing native authentication is preferred; no new API-key requirement is justified. Authentication/tool isolation, Linux containment and the real first conversation loop are explicitly unverified feasibility gates, not missing promises of a working sandbox. Keep them blocked until actual evidence passes; fake protocols cannot complete R7.12. No extra bridge, service or framework is requested.
