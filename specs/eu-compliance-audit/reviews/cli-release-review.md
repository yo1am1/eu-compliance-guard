# CLI, agent bridge and release design review

Date: 2026-10-13. Status: bounded design complete; implementation and acceptance execution pending. This review owns R6, R7 and the R4 execution boundaries/R5 remediation integration. It proposes interfaces, not an implemented application or verified host installation.

## Recommendation and limits

Use one local engine process, one retained result store and small host adapters. Keep legal reasoning instructions canonical in `.agents`; adapters handle discovery, protocol translation and capability reporting only. Start with one dashboard agent bridge using Codex App Server over stdio, subject to installed-version and permission verification. Other hosts remain separate measured integration targets; seven executable names do not establish seven compatible integrations.

Use SQLite and filesystem Evidence storage outside repositories and public package paths. Serve the dashboard from the engine on loopback. CLI calls attach to this engine through a per-user local socket; the client may start it explicitly when absent, under a singleton lock. Scanner, browser and agent subprocesses are bounded workers, not additional permanent services. No separate graph database, queue service, cloud account or new agent framework is justified for the first milestone. Retained reports remain usable without an agent provider or fresh legal retrieval (R6.10–R6.13).

The requirements approve goals, while design and implementation tasks remain pending approval (R7.1). Neither this review nor researched documentation authorizes installation, provider calls, source changes or publication. No EU/national corpus, scanner behavior, host authentication, model quality or performance was validated here.

## Engine and dashboard-to-agent contract

The CLI wrapper and dashboard call the same engine operation dispatcher; neither writes database records directly. Start with versioned JSON requests and persisted engine events. A later stdio MCP shim may translate `tools/list` and `tools/call` into this dispatcher if a host cannot safely invoke the wrapper. It must not become a second engine, permission authority or network service. MCP stdio and local HTTP transport requirements are documented in [T1].

Illustrative public operation names: `capabilities`, `start_audit`, `get_run`, `get_finding_context`, `run_check`, `propose_patch`, `apply_patch`, `retest`, `cancel`. CLI shape: `eu-compliance-guard call`, receiving one JSON request on stdin and returning JSON on stdout; diagnostics go to stderr. This avoids command interpolation, secrets in argv and seven command dialects. Arbitrary shell strings, executable paths and model-provided check scripts are not operations.

| Record/interface | Minimum fields and invariants |
| --- | --- |
| Request | `schema_version`, `request_id`, `project_id`, `run_id` when applicable, `operation`, typed `arguments`, `expected_revision`. Caller identity comes from authenticated transport, never a model-supplied field. |
| Authorization | `grant_id`, authenticated owner, project identity/root identity, allowed operations, allowed paths/test origins, synthetic fixture namespace, external-provider/data categories, budget, expiry/revocation and scope revision. Persist grants privately; carry authorization forward while valid. Only owner interaction can expand it. |
| Finding context | Finding/Obligation IDs, scope revision, source citations and dates, selected redacted Evidence IDs/digests, check results, unresolved facts and project snapshot digest. Send only authorized context; documents remain untrusted Evidence. |
| Agent action proposal | `action_id`, Finding IDs, operation, typed arguments, base revision, target files/origins, diff digest when relevant, intended retests, expected effects. Engine validates against existing authorization; missing authorization creates a pending owner decision. |
| Patch | `patch_id`, base file digests including dirty/untracked content where touched, allowed relative paths, reviewable diff, expected new digests, retest plan, authorization reference and state. Refuse path traversal, binary changes or unsupported operations rather than silently expanding scope. |
| Event | `schema_version`, `project_id`, `run_id`, monotonic per-run `sequence`, `event_id`, `request_id`, optional `action_id`, timestamp, event type and typed payload. Database transaction commits status plus event together; sequence is replay authority. |
| Check/result | Check/assertion ID and version, input/environment/legal-source digests, producer/rule versions, attempts, expected/actual outcomes, evidence_refs, coverage exclusions and execution error. Applicability and verification status are separate fields. |
| Response | `request_id`, outcome (`accepted`, `blocked`, `conflict`, `failed` or completed operation result), engine revision and structured error. Accepting a request is not evidence that its audit/check completed. |

Dashboard endpoints can remain small: `POST /api/requests`, `GET /api/runs/{run_id}`, `GET /api/runs/{run_id}/events?after=<sequence>` as Server-Sent Events, and `GET /api/evidence/{id}`. Socket CLI exposes the same requests/results. Resolve project/Evidence IDs server-side; these routes never accept arbitrary filesystem paths. Select a repository/test URL through an authenticated owner action, not an imported hyperlink.

Bridge lifecycle:

1. Verify executable version/capabilities and processing authorization before sending any repository context. Reuse existing native CLI authentication through its documented mechanism; do not require a new API key, copy authentication files into snapshots or export credentials to the dashboard. Start a bounded native child with explicit argv, cwd, environment and protocol adapter. Do not load unreviewed project plugins/hooks or give it the original repository merely for a conversation.
2. Bind its private native conversation identity to the engine's project/run/action identities. Supply a curated redacted Finding context. Resume only that binding; changing projects creates a new binding. Do not expose native session identifiers in public artifacts.
3. Normalize conversational deltas, tool progress, errors and completion into typed events. Preserve protocol diagnostics privately after redaction. Native tool notifications are observations; engine actions need dispatcher authorization before execution. Unknown schemas/malformed or oversized records block execution.
4. For Codex, handle native command/file approval requests explicitly; refuse actions outside engine scope even if the host's own approval would permit them. Use reviewed CLI/MCP tool access instead of experimental dynamic tools. For other hosts without a proven pre-execution gate, use an isolated proposal-only session or mark executable bridge support blocked.
5. Persist and stream proposed actions separately from text. Apply an authorized patch through engine code, then rerun declared assertions and relevant regressions. Conversation completion, tool completion and process exit cannot set a Finding to verified (R5.15–R5.19).

Native CLI ambient permissions and engine action permissions are separate authorities. The dispatcher can reject an engine action but cannot stop a native agent tool that reads the home directory, executes a shell or transmits source independently. A read-only flag limits some writes; a prompt cannot enforce secret-read or provider-transfer restrictions. No inspected host documentation establishes the complete managed boundary proposed here.

The managed launcher must expose only an explicitly approved redacted snapshot/context and an isolated scratch directory to model-controlled tools. Original repositories, private Evidence stores, home directories, credentials, other local sockets and inherited arbitrary environment values must be inaccessible to those tools. The sole engine channel exposes only scoped dispatcher operations; its transport identity cannot grant broader owner permissions. Disable native direct file mutation, shell/network execution and unreviewed hooks/plugins, or confine them with an OS boundary whose filesystem and network denials are actually tested. Only the engine dispatcher may request original-project reads, checks or patches. Permit approved provider traffic through the trusted host transport; model-controlled tools must not inherit that egress permission or gain access to the host's authentication material. This separation may be unavailable in a given CLI; do not assume a process-wide sandbox can simultaneously expose credentials to the host and hide them from its native tools.

Use existing CLI auth when a documented trusted authentication channel preserves those restrictions. If it requires exposing credentials or broad ambient access to model-controlled tools, managed-agent execution is blocked until an enforceable configuration is demonstrated; adding an API key is not a substitute. Show separate capability fields `engine_actions_enforced`, `native_secret_reads_denied`, `native_mutations_denied`, `tool_egress_denied`, `provider_transfer_authorized`, and `auth_isolation_verified`, each unknown until observed evidence establishes it. Unavailable controls disable executable integration. A proposal-only session also needs an enforced data boundary: it may receive explicitly publishable/synthetic context under approved provider processing, but must not run with access to private project/home data. All seven hosts' managed-agent containment is unknown in this design wave (R4.4, R4.8, R6.8).

## Local security and independent integration challenges

The local machine boundary is not authentication. Bind HTTP only to loopback, validate exact `Host` and allowed dashboard `Origin`, reject unauthorized/null origins, enforce owner session credentials and CSRF protection on state changes, and apply authentication to Evidence and event reads as well. CLI socket is owner-only; validate socket ownership and peer identity on supported platforms. Local browser access must not expose durable grant credentials in URLs, logs or Evidence. MCP recommends Origin validation and loopback binding for local HTTP [T1]; the proposed dashboard controls apply that principle without claiming MCP secures the application.

Resolve and authorize filesystem targets at action time. Symlinks, changed repository identity, paths escaping through archive members and file replacement between validation and use must not bypass root restrictions. Use descriptor-relative safe access or equivalent platform checks; block unsupported safety guarantees. Serve imported code/logs as escaped text, disable raw HTML, use sandboxed artifact views and a restrictive content policy. Scanner messages, graph labels, legal pages and model output can contain scripts or prompt injection (R2.9, R4.16–R4.17).

Test URL permission includes scheme, host, port and permitted routes/actions. Revalidate redirects, resolved addresses and browser requests; block unapproved destinations, metadata endpoints, WebSockets and service-worker/network escapes. A separately approved localhost test origin must not become permission to contact every local service. The MCP security document describes SSRF, redirect and DNS-rebinding risks [T2]; those mechanisms also apply to audit retrieval and browser workers.

Run only reviewed scanner/check commands with fixed argv and authorization. Repository test configuration, package scripts, scanner rules and graph semantic extraction can execute code or send data; source reading permission does not authorize those effects. Retests need the same boundary enforcement as initial checks. Validate scanner schemas/locations, retain errors/exclusions and counter-evidence, and treat rule matches or inferred graph relationships as leads until independently verified (R3.2, R3.17–R3.20, R5.10, R7.11).

Redact before model submission, dashboard rendering and exports, not only after logging. Screenshots/traces can contain tokens and personal data; raw archives stay private with owner-only access and a stated retention/removal policy. Provider availability is separate from permission to transmit data, and a local UI is separate from a locally running model. Core report inspection requires no provider subscription; optional agent features may require separately authorized credentials/access (R4.7–R4.9, R6.11–R6.13).

## Patch conflicts and recovery

Preserve existing user changes by comparing actual file digests with the reviewed proposal's base; a Git commit ID alone misses dirty/untracked files. Hold a per-project engine mutation lock, recheck all affected paths before writing, and journal before/after content for bounded recovery. The lock cannot stop external editors; recheck immediately before each replacement and report any conflict. A crash during a multi-file patch requires inspection/reconciliation; never promise filesystem-wide atomicity. Recovery may restore only files still matching engine-written digests, and must never overwrite later user edits (R5.6, R5.18, R7.13).

States: proposed, running, applied-awaiting-verification, verified, failed, blocked. Approval references the exact diff digest and targets; changed proposals need fresh review only if existing grant no longer covers them. All source patches, including native agent suggestions, go through the shared executor with those preimage/version checks; native direct edits are prohibited. Applying a patch does not close organizational/manual review. Verified requires retained before/after results on matching code/environment/source versions and a counter-evidence disposition. Changed inputs mark affected results stale; if dependency mapping is incomplete, conservatively invalidate the run's technical conclusions (R5.7, R5.10, R5.19–R5.20).

Persist request IDs and payload digests: replaying identical requests returns retained results; reusing an ID with changed content is a conflict. Browser reconnect replays events after the last sequence, deduplicates and verifies project/run binding. It never restarts a patch. Restart marks active workers interrupted, reconciles recorded side effects and retains completed checks. Mutation is not automatically retried after an ambiguous exit. Cancel stops the owned worker group with a bounded graceful period, then termination; keep evidence and show unfinished checks. Resume creates a new attempt after authorization/input checks; preserve inconsistent earlier attempts (R5.9, R5.15–R5.16, R6.12).

## Global install, upgrade and removal

Install from a reviewed versioned artifact containing engine, dashboard build, portable skill/support files, licenses and checksums. Record engine schema and adapter versions together. Prefer a private isolated Python environment using the project's locked dependencies; do not alter global Python dependencies. Select one documented executable location, and report PATH requirements instead of editing shell profiles automatically. No host authentication/settings replacement is needed for simple skill discovery (R6.4–R6.6, R6.9).

A private installation receipt records package/version/digest, each managed path's type and installed content digest or exact symlink target, and narrowly owned configuration keys if unavoidable. This is separate from the upstream source manifest. Proposed interface: `install plan`, `install apply`, `upgrade plan/apply`, `uninstall plan/apply`. Plans are concrete path/content diffs and conflicts; apply never mutates beyond the authorized plan.

1. Inventory destinations without reading authentication files. Refuse an occupied unowned path. If owned current bytes differ from the receipt, report conflict and leave them intact; do not force overwrite. Check name collisions and project shadowing before claiming discovery.
2. Acquire installer lock; stage a complete version privately; verify digests, licenses and runtime compatibility. Recheck destination content before publication. Write adapters atomically per file, then receipt; journal interrupted operations. An identical repeated install is a no-op.
3. Upgrade while engine actions are quiescent. Back up private store metadata/data before schema migration; validate migration compatibility before switching active version. Failure leaves the previous usable version, or an explicit recovery requirement if data was migrated. Never roll an old binary onto an incompatible store. Invalidate affected results after engine/rule changes.
4. Uninstall only receipt-owned paths whose content/targets still match. Preserve edited files as conflicts. Remove only precisely owned configuration entries and never restore an entire older settings file over newer user changes. Leave private audit data by default and state its retained location/removal mechanism privately (R4.9); deleting it needs separate explicit scope.

Do not repurpose the repository adapter `--write` as this installer. Reuse its canonical-content generation and hash conventions, but enforce receipt ownership and conflicts around global writes. Implementation should add one small installer conflict/repeat/interruption fixture, not a general plugin manager.

Exclude generated host directories, credentials, `.env` files, private documents, Evidence/traces/reports, databases, cache/logs, machine/provider settings, live sessions and handoffs. `.gitignore` is insufficient: a tracked file or explicit package inclusion can still leak. Review artifact contents and exact staged diff, including new files and symlink targets (R7.3, R7.7–R7.8).

Keep current unrelated modifications intact. Future supervisor integration reviews disjoint writer diffs and actual verification evidence. Run packaging checks in a clean candidate checkout; run new engine, installer, browser and host cases only with synthetic authorized fixtures. These new gates do not exist yet. An approved candidate still needs explicit publication authority, scoped staging and remote revision verification. Report immutable revision link, release/package version, checksum and installed host matrix; distinguish public release success from global installation success (R7.1–R7.3, R7.6–R7.9).
