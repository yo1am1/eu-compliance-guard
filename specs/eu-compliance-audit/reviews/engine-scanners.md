# Shared engine, storage, events and scanner design review

Date: 2026-10-13. Status: design recommendation, pending integration and approval. This review covers R3.1–R3.20, R4 execution and evidence boundaries, R5.6–R5.9, R5.14–R5.20, R6.10–R6.13 and R7.5/R7.12/R7.13. It defines proposed contracts and acceptance cases; it does not report an implemented or tested application.

## 1. Smallest complete architecture

Use one Python engine, one local SQLite database and an artifact directory outside the public package. Run one scheduler and one authoritative writer. The dashboard and agent CLIs submit the same typed commands and read the same retained results. Tools run as bounded children, not independent application services. No graph database, task broker, LangGraph runtime or compliance logic in host adapters is justified for the first milestone.

The repository actually declares Python >=3.12 and PyYAML >=6.0.3 in [pyproject.toml](../../../pyproject.toml). [scripts/validate.py](../../../scripts/validate.py), [scripts/sync_agent_adapters.py](../../../scripts/sync_agent_adapters.py) and [tests/test_validation.py](../../../tests/test_validation.py) validate instruction packaging; the two existing tests do not exercise an audit backend. [AGENTS.md](../../../AGENTS.md) explicitly distinguishes this instruction library from its described consuming backend. Preserve `.agents` as the canonical instruction layer and its existing provenance rules. Proposed application path: `apps/eu-compliance-audit/`, containing the engine package, HTTP entrypoint, CLI entrypoint and later frontend assets. This path is a proposal, not an existing executable.

Recommend FastAPI plus Uvicorn as separately declared application dependencies. Keep SQLite, JSON, hashing, subprocess supervision and CLI parsing in the Python standard library. FastAPI documents native `EventSourceResponse` and `ServerSentEvent` in `fastapi.sse`, added in 0.135.0; use these rather than a new SSE library or hand-written framing. Pin a reviewed FastAPI release with that capability and a compatible Uvicorn release during implementation. Neither is installed or validated by this review. [FastAPI SSE](https://fastapi.tiangolo.com/tutorial/server-sent-events/), [manual server deployment](https://fastapi.tiangolo.com/deployment/manually/).

The server runs one worker without development reload. It binds loopback only, validates Host and exact Origin, and authenticates local clients; being local is not authorization. FastAPI/Pydantic transport models can also validate CLI payloads so the two interfaces do not acquire different input rules. [Uvicorn settings](https://uvicorn.dev/settings/). Plain stdlib HTTP would save dependencies but require rebuilding streaming, routing and validation around a sensitive local execution API; that is the larger maintenance burden here.

### One writer, including headless CLI operation

Hold an OS advisory lock for the selected private state directory for the full engine lifetime. Use `fcntl.flock` for the proposed first POSIX implementation; a Windows equivalent needs a separate acceptance decision. Acquire this lock before opening writable state, recovering runs, serving commands or launching children. The SQLite transaction lock alone cannot elect an executor or prevent duplicate external actions.

- If the dashboard engine owns the lock, the CLI authenticates to its advertised loopback endpoint and submits commands. It never writes SQLite directly or creates its own execution queue.
- If no engine owns the lock, a headless CLI acquires it, runs the same command dispatcher, scheduler and persistence code in-process, and releases it after completion or safe cancellation. It may expose the same loopback API while active so a dashboard can attach without a second scheduler.
- Two simultaneous starters compete for the lock; the loser attaches to the winner after identity/protocol verification. If an owner exists but its endpoint is unavailable, report `engine_unreachable`; do not bypass the lock or start another executor.
- Endpoint discovery lives in owner-only private state, never in exported skills. Do not put authentication secrets in URLs, process arguments, logs or public reports. Treat an old discovery record as stale until the lock and live authenticated handshake agree.
- A read-only offline report command takes a consistent SQLite read snapshot through shared engine reporting code. It cannot resume checks, patch files or alter results. Database migration requires exclusive engine ownership; an unsupported database version opens only for compatible inspection or reports a migration blocker.

An idempotency key is scoped by project, run and command type. Store the request digest and accepted response in the same transaction as the command's durable state. An exact duplicate returns the existing result; reuse with a different digest returns conflict. This guarantees one accepted command, not exactly-once external effects. Recovery rules below handle actions that might have happened before a crash. R6.10–R6.13.

## 2. Persistent model and contracts

Use explicit versioned JSON records for nested inputs and small relational tables for identity, status and ordering. No ORM is needed. IDs are opaque stable identifiers, not paths or line numbers. Every run-scoped relationship includes `project_id` and `run_id`; composite foreign keys prevent cross-run attachment. Keep check definitions versioned separately from execution attempts.

| Record | Minimum fields and invariant |
| --- | --- |
| Project / authorization | `project_id`, private canonical repository locator, allowed test origins/routes, operation allowlist, processing destinations, authorization version, fixture ownership and expiry/revocation conditions. Paths shown in reports are project-relative. Every executable action rechecks authorization; chat cannot expand it. |
| Audit_Run | `run_id`, `project_id`, `parent_run_id`, protocol/engine version, assessment date, scope/facts digest, input manifest digest, legal-source versions, coverage plan, authorization reference, budgets, creation/start/end times, status and interruption reason. Freeze inputs at creation; a changed audit context creates a successor run. |
| Check definition | Stable `check_id`, version/digest, obligation references, method (`repository`, `browser`, `api`, `document`, `manual`, `organizational`, `specialist`), assertion or review completion condition, required capabilities, input dependencies, requested operations and bounded resource limits. |
| Check attempt | `attempt_id`, run/check/version, attempt number, prior attempt reference, effective input digest, resolved tool/version/edition, rule/configuration digests, fixture/state/environment manifest, redacted invocation, timestamps, execution state, outcome, expected/actual observation, evidence references, errors and exclusions. Never overwrite a failed or inconsistent attempt with a later pass. |
| Finding | Stable `finding_id`, project/control/subject identity, obligation and legal-source references, applicability/rationale, verification method/status, impact, evidence and counter-validation attempt references, owner/action, assessment date, freshness and revision. Keep run-specific assessments as history. Relocation changes source references without silently creating a new legal identity; uncertain identity matching requires review. |
| Evidence | `evidence_id`, project/run/attempt, kind, provenance (`declared`, `documented`, `observed`, `independently_verified`), artifact reference/digest/media type/size, observation time, input digest, relative source location or browser state, capture/redaction policy version, access classification, retention and availability. Unavailable/deleted evidence cannot still count as inspectable proof. |
| Remediation action | `action_id`, finding/run, context digest, target paths and preimage hashes, patch digest, authorization reference, intended retests, state, outcome/error and before/after evidence. Preserve manual review obligations separately. |
| Event | `project_id`, `run_id`, strictly increasing run-local `sequence`, event/schema version, type, subject ID/revision, attempt/action ID when relevant, committed timestamp and bounded structured payload. Unique `(run_id, sequence)`; timestamps do not determine order. |
| Graph artifact | Artifact/digest, producer version, schema version, immutable producer revision if known, source manifest, generation mode, parser versions, diagnostics/exclusions and freshness. Map graph references through an adapter; do not use upstream node IDs as Finding IDs. |

Execution states are `pending`, `running`, `completed`, `cancelled`, `interrupted`; a completed attempt has one assessment outcome: `passed`, `observed_failure`, `unresolved_review`, `blocked`, `not_tested` or `lead`. An operational error produces a blocked outcome with an error reason. Applicability is independently `applicable`, `not_applicable` or `unresolved`; freshness is independently `current`, `stale` or `unknown`. A tool's successful execution does not imply a passing control, and a control pass does not settle unresolved applicability.

Run states are `planned`, `running`, `cancelling`, `completed`, `partial`, `cancelled`, `interrupted`. `completed` means all planned work has a recorded disposition, not all controls pass or all law is covered. A budget expiry yields `partial`; missing scope, human evidence or tool access remains visible. `run.terminal` freezes that run's stream and results; later discussion, changed inputs or remediation uses a linked successor run, preserving stable Finding identity. This avoids reopening a terminal event stream with ambiguous replay semantics.

### Storage and atomic publication

SQLite suits local state with a small number of writers; only the owner writes. Use explicit transactions, parameterized SQL, enabled foreign keys, a database schema version and a bounded busy timeout. Begin with the default rollback journal and durable synchronous settings; SSE readers take short snapshots rather than hold long transactions. WAL is optional only if measured concurrent reads justify it, on local storage and a reviewed SQLite build. SQLite documents both its single-writer behavior and WAL's same-host/network-filesystem restrictions. Python 3.12 provides explicit transaction controls. [SQLite use cases](https://www.sqlite.org/whentouse.html), [WAL documentation](https://www.sqlite.org/wal.html), [Python sqlite3](https://docs.python.org/3.12/library/sqlite3.html).

Commit a result's evidence references, state projection and event together. Before that transaction, sanitize and finalize artifacts to a private temporary file, fsync it, atomically rename it on the same filesystem, and sync the directory where supported. Do not announce success before required evidence is durable. A crash can leave an unreferenced artifact; recovery can quarantine it. A missing/corrupt referenced artifact makes the result evidence-incomplete, not passed. Bound disk use and surface disk-full/write/parse failures. Back up through SQLite's backup facility together with an artifact inventory, not a live database-file copy. Do not store tokens in evidence metadata or export private state with the package.

## 3. Shared interfaces and deterministic inputs

Proposed command payload: `schema_version`, `command_id`, `idempotency_key`, `project_id`, optional `run_id`, `expected_revision`, `authorization_id`, `type`, typed `arguments`. Do not accept arbitrary executable strings or shell scripts. Cap payload size, reject unknown action types and validate ownership and revisions before side effects.

| Interface | Contract |
| --- | --- |
| `POST /v1/projects/{project_id}/runs` | Start a frozen planned audit; validate target, scope and capabilities; return `run_id` and accepted revision. Unavailable capabilities become explicit coverage gaps. |
| `POST /v1/projects/{project_id}/runs/{run_id}/commands` | Dispatch allowlisted `cancel`, `resume`, `discuss`, `propose_patch`, `apply_patch`, `retest` and `import_result`. Return durable action/continuation identity. Revision conflicts return 409 with no side effect. |
| `GET /v1/projects/{project_id}/runs/{run_id}/snapshot` | Return retained run, findings, checks, actions, gaps, terminal flag and `cursor` from one consistent database read transaction. |
| `GET /v1/projects/{project_id}/runs/{run_id}/events?after={cursor}` | Replay committed events after cursor, then tail the same durable log. Streaming never starts checks or patches. |
| `GET /v1/projects/{project_id}/evidence/{evidence_id}` | Resolve an authorized stored artifact ID; no arbitrary path, archive member or remote URL fetch. Return safe media treatment and evidence metadata. |
| CLI `audit / inspect / cancel / resume / discuss / patch / retest / import` | Parse into the same command/query contracts and report model. `patch` means explicit review/apply commands, never implicit scan autofix. These are proposed entrypoints, not commands verified here. |

Deterministic input is a manifest of the engine/check/rule versions, actual input bytes and exclusions, dirty/untracked file digests, configuration digest, fixtures and fixture reset procedure, tool/browser/runtime versions, URL/deployment identity, identities/roles, consent states, locale/region/timezone, synthetic clock/seed when controlled, authorization and relevant legal-source versions. A Git commit alone misses dirty files and deployed differences. Exclude secrets by policy and record resulting coverage exclusions without reading them.

Repository checks consume an authorized read-only snapshot of included files where possible. Record symlink handling, generated files, ignored files and unsupported languages. Runtime checks record what could not be frozen, including external responses and server state. Capture expected/actual values and reproducible assertion steps. A retry is another attempt; contradictory results make the assessment inconsistent/unresolved until explained. Do not pick the passing run or call a live third-party-dependent test deterministic merely because its script is unchanged. R3.9/R3.12/R3.19.

### Freshness and invalidation

Each conclusion declares the files, runtime/deployment identity, project facts, legal sources, check/rule versions, graph artifact and manual evidence it depends on. Compare those digests before execution, result publication and reuse. Recheck before showing an earlier pass as current. Store `freshness_reason`, changed input and detection time; retain historical evidence.

Invalidate affected conclusions when declared dependencies change. If dependency coverage is incomplete, invalidate conservatively for the whole relevant project or legal family rather than trust a graph-derived dependency list. File change notifications are a convenience, not the freshness authority. Unknown deployed versions or expired source review dates produce unknown/stale status. A graph rebuild alone does not invalidate an independent browser assertion, but changes to graph inputs used in applicability/source attribution invalidate that attribution. Show the distinction. Compare facts, code, deployed state, legal versions and Findings as separate dimensions. R5.8/R5.20.

## 4. Ordered progress, snapshot replay and closure

Use native FastAPI SSE for transport and the SQLite events table for authority. `ServerSentEvent.id` is a validated cursor containing run identity and sequence; the JSON envelope also contains project/run identity. Support `Last-Event-ID` for reconnect and `after` for the initial snapshot. If both are present, the validated reconnect header takes precedence. Reject wrong-run, malformed or future cursors. This protocol is proposed; the underlying ID/reconnect behavior is documented by [FastAPI](https://fastapi.tiangolo.com/tutorial/server-sent-events/) and the [HTML SSE standard](https://html.spec.whatwg.org/multipage/server-sent-events.html).

1. Read snapshot and its maximum committed event sequence in one transaction. Return `cursor=C`. Open stream with `after=C`; every later commit is replayable even if it happened before the connection opened.
2. Query durable events strictly after the cursor in sequence order. After replay, poll or wait for commit notifications and query again. Notifications can be lost; they are never the event record. Keep short database reads and bounded client buffers; disconnect a slow consumer and let it replay.
3. Clients discard duplicate sequences, reject mismatched project/run IDs, and request a new snapshot on a gap or unknown schema. Object revision guards prevent a late event from overwriting newer state. Never infer state from agent prose or raw stdout.
4. Keep all events for a retained run in the first milestone; no independent event-log compaction. If retention removes a run, return an explicit unavailable response. A future compaction scheme must return a snapshot-required response for an expired cursor rather than replay an incomplete suffix.
5. Persist exactly one `run.terminal` after final results, cancellation cleanup or interruption disposition. Replay it, then end the response. Clients call `EventSource.close()` when they receive it; EOF alone normally triggers browser reconnection. A snapshot already marked terminal needs no stream. A reconnect whose cursor already consumed terminal receives HTTP 204, which stops EventSource reconnection. A new action after terminal returns a successor run; clients switch explicitly.

Event types include `run.started`, `check.started`, `check.completed`, `finding.updated`, `capability.blocked`, `agent.started`, `agent.completed`, `patch.proposed`, `patch.running`, `patch.applied`, `patch.failed`, `patch.blocked`, `retest.completed`, `inputs.stale`, `run.cancel_requested`, `run.interrupted` and `run.terminal`. Intermediate log messages are bounded diagnostics, not the result model. Disconnecting a subscriber only ends that subscription; cancellation is an authenticated engine command. R5.15–R5.19/R6.12/R7.13.

## 5. Scanner and browser import boundaries

An adapter accepts bytes plus an execution envelope: producer/version/edition, format/schema, input manifest, rule/configuration versions, timestamps, exit code, diagnostics and exclusions. Validate size, nesting, required types and relative source paths before normalization. Store a private sanitized raw-result reference and its digest; retain parser version and normalization warnings. Missing provenance is `unknown`, never invented. An import can be inspected without authorizing execution of its suggested commands, fixes, hyperlinks or rule references.

### Semgrep and SARIF

Prefer pinned Semgrep Community Edition with a small reviewed local rule set for candidate discovery, invoked by a fixed command template. Use local configuration, JSON output, metrics off, version checks disabled, no autofix, no registry `auto` configuration and denied outbound network. These flags do not constitute a sandbox. Do not assume paid cross-file/supply-chain capabilities are present. Exit 0 alone does not mean no findings; exit 1 can indicate findings with `--error`. Check JSON errors, actual scanned paths and skipped rules as well as the exit code. [Semgrep CLI](https://docs.semgrep.dev/cli-reference), [CE languages and capabilities](https://docs.semgrep.dev/semgrep-ce-languages).

For Semgrep JSON map `results[].check_id` to producer rule ID, `path` plus `start/end` to source range, and `extra.message/severity/metadata` to candidate description and producer classification. Retain top-level `version`, `errors`, `paths` and `skipped_rules`. Rule content hashes come from the execution envelope, not assumptions about rule names. Do not require commercial `fingerprint`, snippet or trace fields when CE omits them. [Semgrep JSON/SARIF fields](https://docs.semgrep.dev/semgrep-appsec-platform/json-and-sarif).

Accept SARIF 2.1.0 through a separate small normalizer: read `runs[].tool.driver.name/semanticVersion/rules`, `results[].ruleId`, message, locations/regions, optional fingerprints/suppressions and `invocations[].executionSuccessful/toolExecutionNotifications`. Resolve URI bases only into the authorized input manifest; never fetch remote artifacts. Preserve all locations and unknown extension fields in raw evidence. Reject malformed or incompatible formats with a blocked import, not an empty passing scan. Producer severity is not legal impact; imported fixes are proposals only. [OASIS SARIF 2.1.0](https://docs.oasis-open.org/sarif/sarif/v2.1.0/os/sarif-v2.1.0-os.html).

Generate an internal candidate identity from project, producer/rule version, subject/source anchor and match digest when no producer fingerprint exists. Deduplication groups observations but preserves each attempt and exclusion. A separately versioned rule-to-control mapping suggests obligation candidates; applicability and independent validation are still required. No match means only that this rule found no match in scanned inputs, not that a legal obligation passed. Suppression or ignored files do not close Findings.

Import provenance review must distinguish tool licensing from rule licensing. Semgrep's source LICENSE includes LGPL 2.1; the upstream rules repository points to Semgrep Rules License v1.0, whose terms need review for the intended redistribution/use. Do not copy a registry catalog into the public package on the assumption that it shares the engine's license. Initially write a few synthetic/local rules and retain their provenance. [Semgrep LICENSE](https://github.com/semgrep/semgrep/blob/develop/LICENSE), [rules LICENSE](https://raw.githubusercontent.com/semgrep/semgrep-rules/develop/LICENSE), [official rules terms](https://semgrep.dev/legal/rules-license/). Exact release/artifact licensing remains a release gate, not legal advice established by this design.

### Browser checks

Use Playwright Python with a pinned browser build for the first browser worker. Reuse its tracing and fresh browser contexts, not a custom recorder. Record route, journey, role, consent state, locator/element, assertion, expected/actual observation, deployment identity, configuration and evidence references. Browser trace captures actions, DOM/network information and screenshots; context tracing alone does not capture test assertions, so save assertion results explicitly beside it. [Trace Viewer](https://playwright.dev/python/docs/trace-viewer), [Tracing API](https://playwright.dev/python/docs/api/class-tracing), [BrowserContext API](https://playwright.dev/python/docs/api/class-browsercontext).

A fresh-visitor/reject/accept/withdraw scenario uses separate resettable synthetic contexts with explicit transition ordering. Include pixels, URL identifiers, SDKs, storage, fingerprinting and declared server-side forwarding; browser observation alone cannot prove absent server-side forwarding. Routes, roles, regional/language variants and complete journeys must be a coverage plan with exclusions. Rights/retention/commerce workflows need approved synthetic identities and downstream observation/cleanup; do not invoke real purchases or messages as ordinary browser steps.

Inject a pinned local axe-core bundle if accessibility checks are selected; this uses the same browser worker and avoids a second Node service. Do not equate this Python arrangement with the Node `@axe-core/playwright` example having been tested. Preserve `violations`, `passes`, `incomplete`, `inapplicable`, affected nodes, rule/version/tags and configured exclusions. Manual keyboard, assistive-technology, documents and whole-process evaluation remain separate review items. [Playwright accessibility guide](https://playwright.dev/docs/accessibility-testing), [axe-core README](https://github.com/dequelabs/axe-core). Playwright Python is Apache-2.0 and axe-core is MPL-2.0 in inspected upstream license files; review selected distribution notices before bundling. [Playwright LICENSE](https://raw.githubusercontent.com/microsoft/playwright-python/main/LICENSE), [axe-core LICENSE](https://raw.githubusercontent.com/dequelabs/axe-core/develop/LICENSE).

Full traces can contain credentials and personal data. Default to synthetic fixtures and selective redacted observations; do not retain an unrestricted trace of an authenticated live service merely because it is convenient. Trace capture requiring sensitive artifacts needs explicit storage authorization and a tested sanitization policy; if safe capture is unavailable, record an evidence gap. Never upload traces to a hosted viewer as an implicit inspection step. Serve screenshots as images and untrusted documents/code as escaped text or downloads with safe headers, never executable imported HTML.

## 6. Graphify compatibility and uncertainty

Use Graphify as optional discovery, not a required executor or verdict engine. Import `graph.json` into a small versioned adapter and keep it as an artifact; bounded subgraph queries are enough initially. No NetworkX dependency in the core engine and no separate graph database. A missing graph blocks graph-backed navigation only, not independent repository/browser checks.

Current inspected upstream `v8` metadata declares `graphifyy` 0.9.89 and Apache-2.0, with retained MIT portions documented in NOTICE. The exporter declares `GRAPH_SCHEMA_VERSION = 1`, exports node-link JSON using `nodes`/`links`, and writes `graph.schema_version` and `graph.graphify_version`. These are a candidate compatibility baseline, not an immutable pin: `v8` is a mutable upstream reference. Before adoption select an immutable commit and distribution digest, inspect its complete import schema and retain license/NOTICE files. No installed release or graph output was exercised here. [Graphify metadata](https://raw.githubusercontent.com/Graphify-Labs/graphify/v8/pyproject.toml), [exporter](https://raw.githubusercontent.com/Graphify-Labs/graphify/v8/graphify/export.py), [NOTICE](https://raw.githubusercontent.com/Graphify-Labs/graphify/v8/NOTICE).

For this candidate adapter, require graph version metadata and node/link collections; preserve directed/multigraph information and multiple relationships. Normalize node `id`, label, `source_file`, source location and available extraction origin; normalize link endpoints, `relation`, confidence label/score, source references and available origin. Keep upstream raw fields without silently applying undocumented aliases. Upstream build code handles external stubs and source/provenance fields; an external node with no source location must remain unresolved rather than point at a guessed file. [Graphify build source](https://raw.githubusercontent.com/Graphify-Labs/graphify/v8/graphify/build.py).

Treat `EXTRACTED`, `INFERRED`, `AMBIGUOUS` and unknown provenance distinctly. Static AST resolution may generate inferred edges without an LLM. Keep extraction method (`ast`, heuristic, semantic/model, unknown) separately from confidence; a high numeric score is not a runtime observation. An extracted import proves a source relationship, not that personal data reached a recipient. A semantic/document relationship remains a research lead. [Graphify architecture](https://docs.graphify.com/concepts/architecture), [upstream README](https://github.com/Graphify-Labs/graphify).

Retain the graph's input-manifest digests, parser versions, supported/omitted languages and available diagnostics. Validate unique IDs, endpoint existence, bounded size/counts, finite confidence values, source containment and source-range plausibility. Missing diagnostics mean unavailable, not clean. Missing input digests prevent a current-freshness claim even when the graph has a Git revision. Producer/schema incompatibility quarantines the graph and exposes a navigation blocker; do not silently reinterpret it.

Connect Finding to component/source reference, processing activity and Obligation through explicit engine-owned links containing supporting evidence, author/method and uncertainty. Do not inject legal/processing claims into upstream AST fields. Default future graph generation to reviewed local code-only extraction; semantic documents/media, provider extras, MCP servers, live database introspection and automatic host installation require their own authorization. [Local navigation rule](../../../.agents/skills/graphify-navigation/SKILL.md) already makes source inspection authoritative. Dynamic dispatch and missing/stale inputs remain limitations. No upstream performance or model-savings claim is adopted.

## 7. Safe execution, cancellation and mutation recovery

### Before starting a child

Resolve an allowlisted executable outside the audited repository and record its version/digest. Build an argument array with `shell=False`; use a fixed engine-owned runner and sanitized cwd/environment. Do not inherit authentication, proxy, cloud credentials, `PYTHONPATH`, startup hooks or project-specific executable PATH entries. Provide only required runtime variables and an isolated tool home/cache/temp directory. Do not import target modules, execute target scripts, run package-manager hooks or load arbitrary repository plugins as discovery. Python documents environment replacement, process-session creation and shell risks. [Python 3.12 subprocess](https://docs.python.org/3.12/library/subprocess.html).

Enforce read-only repository/input mounts and allow writes only to private attempt output or explicitly authorized synthetic targets. Apply output, file, memory, process-count and wall-time limits. Run deadline accounting on a monotonic clock. Drain stdout/stderr concurrently with caps so a full pipe cannot hang the child; redact before retained logging. Limit execution to one active check initially, keeping the engine responsive while awaiting child I/O.

An argument allowlist and cwd are not filesystem/network containment. The proposed initial supported execution platform is POSIX/Linux with a reviewed sandbox and process containment mechanism; exact support remains open. If sandboxing cannot be established, block execution that depends on isolation. A synthetic trusted-fixture mode can have a separately stated boundary but cannot imply safe scanning of arbitrary repositories.

Static scanning has outbound network denied. Browser execution permits only authorized test destinations, including subresources, redirects, WebSockets and service-worker traffic; enforce this below the page rather than rely solely on Playwright route callbacks. Restrict private/link-local/metadata destinations and DNS changes, except exact explicitly granted test endpoints. The audit application's own API port is never a permitted target destination. Tool downloads and rule refreshes are explicit setup/research operations, not scan-time fallbacks. External agent calls receive only scope-approved context; offline Findings remain available when providers or legal research fail. R4.4–R4.9/R4.16–R4.17/R6.13.

### Cancellation and restart

Persist cancellation before stopping scheduling. Signal the owned POSIX process group created with `start_new_session=True`, allow a short bounded grace period, then kill remaining children, drain bounded output and reap them. Cancelling a coroutine or killing only the immediate parent is insufficient. Process groups cover cooperative descendants; detached children require OS containment (for example a reviewed Linux cgroup/sandbox supervisor with owner-death cleanup). Support cannot be claimed until that platform mechanism is tested. Do not signal arbitrary persisted PIDs after restart because PID reuse can affect unrelated processes.

Proposed defaults for review: 10-minute run budget, 60-second check budget, 5-second termination grace and 10 MiB retained diagnostic output per attempt. These are product limits, not benchmark claims; browser/specialist checks can declare separately authorized limits. If children cannot be confirmed stopped within the shutdown bound, mark cleanup blocked and execution safety unresolved; do not report safe cancellation or start conflicting work.

Keep finalized completed evidence. Mark active attempts cancelled/interrupted and queued work not tested with explicit reasons. On restart, acquire sole ownership, reconcile owned containment handles, journaled actions and artifact integrity, then mark prior in-flight work interrupted. Never automatically repeat a possibly mutating action. A resume creates a linked run with fresh authorization/input checks; it may reference matching completed evidence, visibly as reused, and creates new attempts for remaining work. A browser journey resumes at a clean fixture/check boundary, not midway through an unknown account state. Expired authorization or uncertain fixture cleanup blocks it. R5.9/R6.12/R7.13.

### Patch preimages and conflicts

Remediation states are `proposed`, `running`, `applied-awaiting-verification`, `verified`, `failed` and `blocked`. A patch proposal freezes all target preimage byte hashes (including dirty content), file types/modes, relative paths, expected absences for new files, diff digest, authorization and retest plan. The UI/CLI shows these before application. The engine revalidates them under a project mutation lock immediately before writing. Reject changed/deleted targets, symlinks, path escapes and additions whose destination now exists. Do not fuzzy-apply a patch, checkout a branch, reset unrelated edits or treat successful patch application as verification.

The first automatic apply supports one existing regular file. Build postimage privately, record the action journal, recheck the live preimage and atomically replace that file on the same filesystem. Preserve modes and unrelated content. The engine lock serializes its own writers only; it cannot prevent an unrelated editor writing between preimage comparison and replacement. Therefore direct automatic application also requires a controlled exclusive-write window for the target. If that cannot be established, provide the reviewable patch for owner application and mark automatic apply blocked. Do not claim hashes provide atomic compare-and-swap against arbitrary writers. Wider multi-file automatic apply is deferred until its partial-write recovery is approved; it is not needed for the first slice.

After crash, compare the file with journaled preimage/postimage: preimage means not applied; postimage means applied-awaiting-verification; any other content is conflict/unknown. Never rollback over new user edits. A successful apply invalidates affected old results and graph attribution before launching the retest. Verification requires retained before/after assertions and relevant regressions against recorded postimage/deployment versions. A stale pass, agent statement, absent scanner match or rebuilt graph cannot close the Finding. Missing redeployment, flaky results or manual evidence keeps it open. R5.6–R5.7/R5.18–R5.20/R7.13.

## 8. First synthetic vertical slice and acceptance cases

Use one small synthetic repository and local test page with a deliberate tracker request before the fixture's consent condition is met, a safe control and a notice describing the intended behavior. Route the tracker to a synthetic authorized receiver; no real third-party request or personal data. The named control is an engineering assertion with separately sourced applicability, not a universal rule that every tracker requires consent. A manual retention/governance item remains unresolved.

One reviewed local Semgrep rule finds the tracker call as a lead. The Playwright check establishes an observed pre-consent request, with route/state/assertion/network evidence and an established source link or explicit unresolved mapping. Dashboard and one CLI inspect the same Finding. An evidence-linked discussion explains the observation and counter-evidence; model unavailability blocks discussion without hiding the Finding.
