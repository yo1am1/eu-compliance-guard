# Local frontend and evidence-linked chat — design review

Date: 2026-10-13. Status: bounded design complete; implementation and acceptance execution pending.

This review owns R3.18–19, R4.7/16–17, R5.12–20, R6.10–14 and R7.12–13 in [the approved requirements](../requirements.md). [The research record](../research.md) supplies the prior scanner, graph and browser-evidence rationale. Requirements are approved; the older research statement calling them a draft is historical. This repository currently supplies instruction packaging and Python validation, not an existing application UI. No consuming backend or external repository is assumed available.

## Recommended minimum

Build one finding-centered dashboard served by the same local process as the shared engine. Use React and React DOM for the related selection, evidence, conversation and action states; TypeScript for the API model; Vite only for development/build. Serve the built static assets in production without a second frontend server. Native fetch and EventSource cover request/response and progress. Plain CSS, system fonts, semantic controls, a unified text diff and an expandable relationship list cover the first milestone. No hosted account, analytics, remote assets, graph database, IDE, embedded target browser or custom recorder.

This is a design recommendation, not a claim these dependencies are installed. [React's official guidance](https://react.dev/learn/build-a-react-app-from-scratch) describes the tradeoff of a client-only build: routing and data fetching remain application responsibilities. This bounded local screen needs neither server rendering nor a general routing framework. [Vite's guide](https://vite.dev/guide/) documents static build output and TypeScript templates. Pin compatible versions and review licenses during authorized implementation; no version or performance claim is made here.

Server-rendered HTML with a small script has fewer build dependencies, but maintaining five synchronized views, chat drafts and ordered event reconciliation would require substantial manual DOM state. React is the modest choice for this scope. Defer state libraries, query libraries, CSS frameworks, component suites, rich Markdown, syntax highlighting and graph layout libraries until a demonstrated gap requires one. A relationship drill-down satisfies the repository-map task without a force-directed canvas. Use the shared engine/result model agreed in engine design; never reimplement legal applicability or check execution in the browser. R6.10–11.

## One dashboard and its owner journey

The purpose is to decide what failed, inspect why, authorize a bounded change when necessary, and inspect its retest. Use neutral surfaces, readable system type, one action accent and explicit text labels for status. Group with spacing and alignment. Screenshots and evidence receive space before decorative summaries.

1. **Project and scope header.** Show the selected project, environment/test target, assessment date, run identifier, input revision, scope revision, permitted operations and connection freshness. Before a run, use a short repository/test-URL form resolved by the backend into an authorized project. A browser file input cannot grant general repository access. Show included/excluded journeys, jurisdictions and unresolved facts in a scope disclosure. Starting a run uses the established permission scope; selecting a different target does not inherit permission automatically.
2. **Finding list.** Provide status and impact filters, text search, explicit coverage gaps and counts by disposition. Each row has a stable identifier, title, verification status, freshness and impact. Applicability remains a separate field. Default to actionable failures and gaps, with passing checks accessible. An empty filtered result says “No findings match these filters”; a project with no completed checks says “No checks completed.” Neither means compliance. Keep sorting stable while work runs; expose a “New findings” button instead of moving the focused row.
3. **Selected finding.** Present control and applicability rationale, authority type/article/jurisdiction, source version and last verification date, expected/actual assertion, evidence strength, missing evidence, remediation owner/history and residual manual review. Evidence links open the retained artifact and exact attempt, not the live target. Browser failures show captured route, tested role/consent/language/region, locator, capture time and screenshot or DOM/network evidence. Before and after have separate labels and metadata. Source references show project-relative file, line range, revision and mapping basis. “Source mapping unresolved” remains explicit when a browser element cannot be tied to source.
4. **Relationship drill-down.** From the finding, expand identified component, processing activity and obligation links. Every edge carries “Structural observation”, “Runtime observation”, “Inferred” or “Unresolved”, producer/schema version, input digest, supporting source reference and available diagnostics. Missing links say “No mapped relationship”; they do not imply no processing. Cycles use visited-node links; show a bounded neighborhood with an explicit truncated count and “Load more”. Stale graph inputs display a warning and cannot establish current source mapping. No graph-derived legal conclusions.
5. **Discuss and remediate.** A finding-scoped conversation shows its bound run, finding revision and selected evidence/source references above the composer. The owner can ask for explanation, propose a change, inspect a read-only diff and request apply/retest. Display affected files, base revision, intended affected/regression checks and permission coverage before execution. Retests use the engine's checks and retain every attempt. Switching findings preserves separate drafts and conversations; delayed responses stay attached to their original finding.
6. **Live timeline.** A collapsible ordered list shows check starts/results, finding revisions, agent actions, patch operations, retests and interruptions. Each entry links its run and entity. Show actual completed/blocked/remaining counts; an unknown total remains unknown. Token fragments may appear in the chat but never drive execution state. Let the owner pause visual updates and inspect earlier events while collection continues. “Show latest” restores follow mode without stealing focus.

At wide desktop widths, use a list beside the finding detail; conversation/diff remains within detail and the timeline follows below. At narrow widths or zoom, stack list and detail, with a “Back to findings” control restoring the previous row and scroll position. No essential action depends on hovering, dragging, a canvas or horizontal page scrolling. Long locators/URLs wrap; source/diff blocks can scroll independently. The same selection has a shareable local URL containing opaque project/run/finding identifiers, never credentials, document text or raw filesystem paths. R5.12–18, R6.11/14.

## Accessible states and interaction

Use landmarks, headings, labelled form fields, native buttons/links, a semantic finding table or list and expandable disclosures. Ordinary navigation uses Tab/Shift+Tab and Enter/Space without custom keyboard modes. Explicitly selecting a finding focuses its heading; background events never move focus. Returning restores focus to its row, or the list heading if that row was removed. Dialogs are reserved for a new permission grant or consequential decision; label them, contain focus, provide Cancel/Escape, and return focus to the invoking control. Existing authorization does not require repetitive confirmation.

Show loading, empty, filtered-empty, selected, running, unavailable, failed, blocked, stale, interrupted and recovery states in text. Disabled controls have adjacent reasons such as “Apply unavailable: source revision changed.” Field errors identify the field and correction without discarding values. Retained evidence stays readable when the provider or legal retrieval is unavailable, with dates and blocked capabilities visible. No red/green-only distinctions.

Announce coalesced meaningful progress politely; announce actionable errors immediately. Do not announce each chat token or every event. Provide a persistent status message and timeline for details. Honor reduced motion; avoid forced chat autoscroll when the owner is reading earlier messages. Sticky areas must not hide focused controls. These decisions follow W3C guidance on [status messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html), [reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html) and [focus not obscured](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html). WCAG 2.2 AA is the proposed engineering target; it does not settle EU/national legal applicability. R6.13–14.

## Thin shared API contract

Names below are illustrative interfaces, not implementation. The engine owns persistence, authorization, revisions, applicability and transitions. The frontend renders server state and validates response shape; the CLI consumes the same engine entities.

| Scope/run snapshot | `schema_version`, `project_id`, `run_id`, `run_revision`, `scope_revision`, `assessment_date`, `environment_id`, `input_versions`, `permission_scope`, `capabilities`, `coverage_gaps`, `last_event_sequence`, `run_state`. Input versions include source/deployment, fixture/config/environment, facts, legal corpus and graph. Snapshot and sequence represent one atomic retained state. |
| Finding | `finding_id`, `revision`, `obligation_id`, `applicability`, `authority_refs`, `impact`, `verification_status`, `freshness`, `stale_reasons`, `check_attempt_ids`, `evidence_ids`, `source_mapping`, `remediation_ids`, `manual_review`. Applicability, check outcome, remediation and freshness are independent. |
| Check attempt | `attempt_id`, `check_id`, `tool_version`, `fixture_version`, `config_version`, `environment_version`, `input_versions`, `steps_or_assertion`, `expected`, `actual`, `outcome`, `started_at`, `ended_at`, `retry_of`, `evidence_ids`, `execution_error`, `exclusions`. No passing retry overwrites a failure. |
| Evidence | `evidence_id`, `project_id`, `run_id`, `attempt_id`, `kind`, `capture_time`, `digest`, `size`, `media_type`, `safe_preview_id`, `redaction_status`, `retention_state`, `browser_context`, `source_refs`. Browser context includes route, tested state, locator/element and viewport. Redacted preview has its own digest; raw artifacts are not ordinary frontend responses. |
| Source mapping | `state` (`established`, `candidate`, `unresolved`, `stale`), `project_relative_path`, `line_range`, `source_revision`, `basis_evidence_ids`, `producer_version`, `reason`. Candidate locations cannot be labelled established. A locator alone proves no source correspondence. |
| Graph neighborhood | `graph_id`, `producer_version`, `schema_version`, `input_versions`, `freshness`, `diagnostics`, nodes and typed edges with provenance/source references, `truncated`, `next_cursor`. Graph absence does not block evidence review. |
| Conversation/action | `conversation_id`, `message_id`, `project_id`, `run_id`, `finding_id`, `finding_revision`, `context_refs`, `processing_boundary`, `action_id`, `action_state`. Context references record versions/digests and actual permitted evidence supplied; generated claims remain attributed agent text. |
| Remediation | `remediation_id`, `revision`, `base_input_versions`, `affected_files`, `diff_digest`, `intended_retests`, `permission_ref`, `state`, `before_attempt_ids`, `after_attempt_ids`, `manual_review`, `error`. A permission applies to the exact operation/targets; diff revision changes require revalidation. |
| Event | `schema_version`, `project_id`, `run_id`, `sequence`, `event_id`, `occurred_at`, `type`, `entity_id`, `entity_revision`, `input_versions`, `payload`. Sequence orders durable events within the run; timestamps are display data. Payloads contain bounded redacted summaries/references. |

Minimal endpoints:

- `POST /api/projects/resolve` resolves a repository/test target and returns its validated identity and scope needs. `POST /api/projects/{project}/runs` starts an authorized run; it does not discover new authorization implicitly.
- `GET /api/projects/{project}/runs/{run}/snapshot` returns retained state and a replay watermark. Paginated finding/evidence/attempt/history/graph reads remain project/run scoped. Lists include a revision and cursor; artifact bytes are served through evidence identifiers, never a path parameter.
- `GET /api/projects/{project}/runs/{run}/events?after={sequence}` supplies ordered SSE. SSE `id` carries the durable cursor. Reconnects accept `Last-Event-ID`; the explicit `after` cursor bootstraps a newly created stream after reload. On automatic reconnect, a valid `Last-Event-ID` takes precedence over the original `after` query; reject invalid/out-of-run cursors. EventSource reconnect and event-ID mechanisms are specified in the [WHATWG HTML Standard](https://html.spec.whatwg.org/multipage/server-sent-events.html); they do not themselves provide durable replay or command deduplication.
- `POST /api/projects/{project}/runs/{run}/conversations/{conversation}/messages` accepts finding revision, selected context references and text. Return a durable message/action identifier; provider failure appears on that action. A response cannot silently create mutation permission.
- `POST /api/projects/{project}/runs/{run}/actions` accepts the operation (`propose`, `apply`, `retest`, `cancel`), target entity/revision, expected input versions, reviewed diff digest, permission reference and client request identifier. Return `202` and the retained action identifier when accepted. Reusing an identifier with the same body returns the existing action; a different body is a conflict. Cancellation is a recorded request until the engine acknowledges it.

Use structured errors with `code`, safe message, affected field/entity and recovery action: unauthorised scope, revision conflict, missing resource, blocked tool/provider, invalid schema/cursor, or expired replay history. Never return a secret-bearing tool traceback. The owner sees the reason and retained work, not an empty panel. Unsupported schema versions stop live updates and offer reload/update guidance. R4.16–17, R5.15–18, R6.10–13.

## Applied, verified and stale semantics

The engine emits `proposed`, `running`, `applied-awaiting-verification`, `verified`, `failed` or `blocked` remediation states. Proposed includes a reviewed diff and intended retests; running identifies the actual operation. Successful application means only that the scoped patch was applied. Verified requires retained failing/before evidence, passing affected and relevant regression assertions against the post-change input versions, and no inconsistent attempt being hidden. A failed apply can still have changed files; retain partial-application evidence and require recovery review rather than auto-rollback over user edits.

Verification of a technical fix does not resolve a remaining document, organizational or specialist review. Show, for example, “Technical retest passed; manual review pending.” Agent statements, patch success, graph edges and historical passes cannot close a finding. When a source/deployment/fact/legal/graph input changes, the engine marks affected conclusions stale with reasons. If dependency mapping cannot establish the affected set, conservatively invalidate the relevant run conclusions instead of guessing they remain valid. Retain historical passes labelled with their original versions. A failed retest, tool crash, cancellation or expired budget preserves partial work and unresolved findings. R3.19, R5.19–20, R7.13.

## Reconnect, reload and conflicting work

On initial load, read a snapshot with sequence N, then subscribe after N. The server retains/replays events created between these operations. Deduplicate by run and sequence/event identifier. Discard events for another project/run and older entity revisions. A sequence gap, malformed payload or unknown schema triggers a snapshot refresh; avoid guessing state from partial events. If the cursor expired, replace the projection with a new atomic snapshot and subscribe from its watermark.

During disconnection, keep retained data visible with “Updates disconnected; last synchronized …”. Disable execution controls until authoritative state is refreshed. On reconnect, catch up before indicating live status. Switching project closes the old stream and cancels pending reads; also check returned identities before updating the screen. History and selected evidence remain anchored to their run. Do not replay a POST merely because the stream reconnected.

After a lost command response, query the retained action by client request identifier before retrying. Browser reload stores only navigation/filter preferences; snapshots, conversation messages and execution state live in the engine store. Unsaved draft loss is disclosed before navigation; drafts need not be stored persistently. After process restart, reconcile interrupted actions with persisted operations/input versions. Read-only history remains available, but interrupted mutations never resume automatically. Two clients proposing/applying against the same source revision receive one accepted operation or a conflict; the losing client refreshes and reviews the updated diff. R5.16, R6.12, R7.13.

## Privacy-safe evidence and local boundaries

Render imported code, scanner messages, legal excerpts, chat and diffs as escaped text. Display validated HTTP(S) source links with external-link labels; block executable/file URL schemes and automatic remote image/resource loading. Do not mount captured HTML or SVG into the application DOM. DOM evidence is inert text; screenshot previews are validated raster images with contextual descriptions and a textual assertion alternative. Large/unsupported/deleted artifacts show metadata and an explicit availability reason. [OWASP's XSS guidance](https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html) supports context-safe rendering and warns that framework escape hatches and unvalidated URLs defeat ordinary protections.

Redact credentials, tokens and unnecessary personal data before evidence reaches logs, previews, chat payloads or exports. Redaction covers DOM, screenshot pixels, URL queries, network headers/bodies, diff content and error messages. A failed/unknown redaction result blocks preview and export; offer safe metadata and a request for a sanitized capture. Preserve what was removed and whether that limits the conclusion without showing removed values. Client-side masking after delivery is insufficient. No telemetry or browser persistent cache of evidence; private responses use `Cache-Control: no-store` and no service worker. Artifact retention/removal is visible, and deletion leaves a history tombstone rather than silently removing a finding's evidence link. R4.7/17.

Use loopback binding, an explicit allowed Host/origin set, same-origin assets/API/SSE and authenticated local sessions. Validate Origin on reads with one and reject untrusted cross-origin access; protect mutations with server-validated CSRF tokens and origin checks. No wildcard CORS or credential in a stream URL. The backend enforces project/evidence membership, canonical path containment including symlinks, allowed test destinations/redirects and operation permission on every action. Identifiers are lookup keys, not authorization. Frontend disabled buttons are usability aids only. [OWASP's CSRF guidance](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html) supports token/origin controls; loopback alone does not authorize a browser request. R4.16–17.

For detailed browser history, reuse Playwright capture capabilities; do not build a recorder. [Playwright Trace Viewer](https://playwright.dev/docs/trace-viewer) provides captured actions, DOM and network inspection and documents local viewing. Expose a local viewer action only for a trace proven sanitized and isolated from the dashboard origin, with no allowed remote fetching; otherwise keep metadata and safe extracted previews. Never upload private traces to a hosted viewer automatically. Trace capture must include the relevant failing attempt and retain retries, rather than adopting retry-only capture as sufficient evidence. R3.18–19.

## Open decisions and integration obligations

1. Supervisor/engine design must settle the shared schema and atomic snapshot/event replay store, cursor retention, revision invalidation and command deduplication. The proposed frontend relies on these guarantees; SSE alone supplies none of them.
2. Confirm supported browser versions and screen-reader combinations. Proposed WCAG 2.2 AA target is an engineering decision, not a legal coverage determination.
3. Security/evidence design must settle local session bootstrap, allowed hosts/origins/targets, retention duration, redaction failure policy and sanitized trace-viewer isolation. Safe extracted previews are the first milestone default; do not expose raw traces to compensate for incomplete redaction.
4. Agent bridge must define processing boundaries and source/evidence context manifests using the shared run identifiers. Provider unavailability must not block inspection; provider success must not create permissions or verification.

No new platform, visual identity exercise or rich editor is needed for acceptance. The listed decisions require cross-review before implementation, not additional features in this assignment.
